# 材料包：桌面端能否做到「N ≥ 6 个满配视频组件、且曲线好看」

> 版本基线：`v1.10.489`（vc603）。问题只有一句：
> **标准 AppWidget（RemoteViews + `setImageViewBitmap`）+ vivo 桌面 `com.bbk.launcher2`，
> 能不能让 6 个组件同时播放 720p/50fps（或更高）的视频动图，并且不掉帧、不烫到降频？**
> **硬约束（不可谈）：画质不降、帧率不降。**「满配」= 内容不被缩小 + 50fps 不动摇。
> 所以本材料**不接受**「降到 25fps」「降分辨率换路数」「用静态图凑数」这类答案；
> 如果物理上做不到，请直接说「做不到」并给出**卡在哪一条物理量**上，以及唯一还能动的是什么。

---

## 一、我们的管线（一句话一图）

```
用户选视频 → App 逐帧合成（圆角蒙版 + 阴影 + 边框）→ 编码落盘 → 播放时每 20ms 推一帧
```

播放有两条通道，**每帧二选一**：

| 通道 | 做法 | 谁在解码 | 现状 |
|---|---|---|---|
| `URI` | `setImageViewUri(files/push/w<id>/<stamp>/fNNNNN.webp)` | **桌面**（AOSP `ImageView` 硬编码 `ALLOCATOR_SOFTWARE`） | 小画布用；桌面每秒只能解约 64Mpx，N=3 就卡 |
| `位图共享` | 我们解码 → `asShared()` → `setImageViewBitmap`（Binder 只传 fd） | **我们** | 大画布默认走这条，N=1/2 实测 50fps |

判据（实测校准）：`画布像素 × fps ≥ 16Mpx/s` 就走位图共享。

**我们能控的量**：画布尺寸、每帧解码成本、推送频率、推哪一帧。
**我们不能控的量**：桌面什么时候 apply、apply 几次、传不传纹理、掉不掉帧。

---

## 二、已实测的数据（全部来自真机日志，可核对原件）

设备：vivo，桌面 `com.bbk.launcher2`。测试素材：1920×1080 / 50fps / 235 帧视频。

### 2.1 单帧成本

| 项 | 实测 | 出处 |
|---|---|---|
| WebP（带 alpha）解码 1280×720 | **12.4 ms** | `W48`（隔离线程、5 次中位数） |
| JPEG（无 alpha）解码同尺寸 | **6.3 ms** | 同上 |
| JPEG + `DST_IN` 常驻 alpha 合成 | **0.4 ms**（合计 6.6ms） | 同上 |
| 管线内实测解码（含 `asShared`、分配） | **10~13 ms** | `W23 解码均` |
| 单次推送（新建 RemoteViews + Binder） | **2.4~3.2 ms** | `W10 单帧均` |
| 我方解码吞吐上限（单核） | **71 Mpx/s**（0.92Mpx ÷ 13ms） | 推算自上面 |

### 2.2 优化做了哪些、效果多少（2 个同素材组件、720p50、每 3 秒窗口）

| 版本 | 解码次数 | 单次 | 解码总耗时 | 折算 |
|---|---|---|---|---|
| 优化前 | ~301 | 13.3ms | 4.06s / 3s | **1.35 核** |
| 只有 A（跨组件共享解码） | ~150 | 13.3ms | 2.00s | 0.67 核 |
| 只有 B（JPEG + 常驻 alpha 分层） | ~301 | 10ms | 3.01s | 1.00 核 |
| **A + B（当前 489）** | **149** | **10.5ms** | **1.56s** | **0.52 核** |

- A = 同素材 N 路「解一次、N 路共用」+ 同一帧并发去重。命中率正好 50%（每帧总有一路必须先解，这是上限）。
- B = 内容帧出 q95 JPEG，形状/阴影/边框烘成**一张常驻 alpha**，播放时 `DST_IN` 乘回去。
  烘时自检：**MAE 0.6/255**（肉眼零差），日志 `W49`。
- 两路现在的实际表现：`实测 50.0~50.3fps`、`帧隔 p95=22ms`、`掉帧 0~1`（偶发 1 次与温控同量级）。

### 2.3 桌面侧我们测得到的

- `桌面取用=0次`（位图共享通道下桌面不解码）。
- 每秒 **100 次** `updateAppWidget`（2 路 × 50fps），每帧 3.7MB 纹理上传 ⇒ **370MB/s**（2 路）。
- **测不到**：桌面实际画了几帧、apply 是否被 cancel、executor 有几个槽位。

## 三、已经证伪、不要再提的方案（附我方证据）

| 方案 | 为什么不行 |
|---|---|
| 布局里放两层（内容 JPEG + 常驻 overlay） | overlay 只能往上叠，擦不掉下面的内容 ⇒ 圆角必露方角。我们按真实几何出图：四角方角面积 **0.60%** 画布（铺满档 2.22%），像素最大差 **205~239** |
| 动画 WebP 单 URI 自播 | `setImageViewUri` 在 API28+ 虽返回 `AnimatedImageDrawable`，但 AOSP 全链路**无人调 `start()`**，只显示首帧；API≤27 只解首帧。两份独立分析一致（APK 内置 `<animated-image autoStart>` 资源才播，运行时素材不适用） |
| `clipToOutline` 交桌面裁圆角 | 要求内容满铺格子、半径编译期固定，与我们「画布与格子解耦 + fitCenter + 半径随尺寸」冲突 |
| `AdapterViewFlipper` / sprite sheet | 相关方法非 `@RemotableViewMethod`，`ActionException` |
| 自绘 Surface / HardwareBuffer 通道 | `RemoteViews` 全类无 `Surface`/`HardwareBuffer`；`INFLATER_FILTER` 只放行 `@RemoteView` |
| 整帧 JPEG | 整帧要自带圆角/阴影 alpha，JPEG 给不了（B 是「内容 JPEG + 别人给的 alpha」，不是整帧） |

## 四、N≥6 的账（硬约束下）

### 4.1 先把「满配」定死

| 口径 | 含义 | 单路需求（50fps） |
|---|---|---|
| **A 画布 = 源像素**（严格） | 1920×1080 内容 1:1 不缩 | **103 Mpx/s** |
| **B 画布 ≥ 组件像素**（我们 v477 定的口径） | 画布不小于屏幕上的格子（本机 **662×643px**），内容不被缩小 | 720p 画布 = **46 Mpx/s** |

当前实现：50fps 档把画布封在 1280×720（`W47` 记 `清晰度 FAIL 0.67×`，因为源是 1920×1080）。
**按口径 B，1280×720 已经满足（1.19× 格子）；按口径 A 还差一档。** 请分别回答两种口径。

### 4.2 我方 CPU（实测校准：单核解码 71 Mpx/s）

| 场景 | 解码需求 | 折核 | 推送（6 路） | 结论 |
|---|---|---|---|---|
| 口径 B · 720p50 × 6 · 同素材 | 46 Mpx/s（共享后 1 份） | 0.6 | 0.9 | **有机会**，总 ~1.6 核 |
| 口径 B · 720p50 × 6 · 6 个不同素材 | 276 Mpx/s | 3.9 | 0.9 | 勉强（热降频是风险） |
| 口径 A · 1080p50 × 6 · 同素材 | 103 Mpx/s | 1.5 | 0.9 | 解码可，**桌面侧 6×8.3MB/帧**是未知 |
| 口径 A · 1080p50 × 6 · 不同素材 | 620 Mpx/s | **8.7** | 0.9 | 单核 71Mpx/s ⇒ 8 核全解也不够 |

### 4.3 桌面侧（我们测不到的部分）

6 路 720p50 = 每秒 **300 次 `updateAppWidget`** + **1.1 GB/s** 纹理上传；
6 路 1080p50 = 每秒 300 次 + **2.5 GB/s**。
外部上一轮的判断：AOSP 每次新帧到达即 `cancel()` 上一次未跑完的 apply，vivo 的 apply executor
很可能是**固定小池** —— 若如此，N 大时的瓶颈是**串行排队**，不是我们的 CPU。

### 4.4 不降画质、不降帧率的前提下，还能动的只有四件事

1. **让每帧更便宜**：JPEG 已经用上（12.4→6.3ms）；还能不能更便宜（硬件解码/GPU 合成）？
2. **让每帧只解一次**：同素材已做到（A，命中 50% 上限）；不同素材无法共享。
3. **让桌面少做事**：能否只更新「帧内容」而不重建 RemoteViews / 不重传纹理？
4. **让波峰摊平**：错相位推送（20/6ms）能否化掉 executor 的串行排队？

## 五、请外部回答的问题（尽量给「能/不能 + 依据」）

## 八、补上：**六路 720p50 的真机实测**（这是材料里唯一缺的那块，现已补上）

设备同前，6 个组件（id 442~447）**同一个素材**（236 帧 / 1920×1080 源 / 50fps），画布全部 1280×720。

| 指标 | 实测（每 3 秒窗口） |
|---|---|
| 我方推送 | **300.0 次/秒**（`渲染=900 次 / 3000ms`），`唤醒迟到均=0ms` |
| 解码次数 | **152 次 / 900 次推送**（共享 42% + 同帧去重 373，`合计省=748/1273`） |
| 单次解码 | 11 ms（分层帧） |
| 我方总 CPU | 解码 152×11ms + 推送 300×1.4ms ≈ **1.0 核 / 8 核** |
| 每路帧率 | **50.0 fps**（`掉帧=0`、`帧隔 p95=21~23ms`、`迟到>8ms=0`） |
| 六个预读环 | 全部 `预读3/环6/回0/空0/败0` |
| 磁盘 | 396MB（6 × 66MB） |
| PSS / native | 150MB / 63MB |

**降频窗口里的退化**：CPU 从 1787MHz 掉到 1107~1500MHz（`掉 16~20%`）的那些窗口，
每路掉到 48.3~49.2fps、`掉帧 2~4`、`最大 85~102ms`。**热设计已经是下一个边界**，不是算力。

**这张表能证明什么、不能证明什么**（三家复核都强调过）：

- 能证明：我方在 6 路时仍有余量（1 核 / 8 核），300 次/秒的提交是稳的，扫帧率不是我们这边的问题。
- **不能证明**：桌面真的画了 50fps。`W10` 只数我们自己发了多少次；被 launcher `cancel` 的帧永不显示，
  而日志照样显示 50.0fps。这一条仍然只能靠**屏录帧差**（工具：`scripts/screen-fps.py`，
  已用已知答案的样片自测：60fps 片读 59.6/s、20fps 片读 19.6/s）。

## 九、因此现在只剩两个可能

1. **屏录显示每路 ≈50fps** ⇒ 720p50 × 6 独立组件**成立**，材料里的 `T_apply ≤ 3.33ms` 被真机满足；
2. **屏录显示 25~35fps** ⇒ 桌面到顶，唯一不违反「画质不降、帧率不降」的解是
   **把 6 个 host 合成 1 个 host（一个 RemoteViews 里 6 个 ImageView）**：apply 从 300/s 降到 50/s，
   门槛从 3.33ms 回到 20ms；纹理带宽 1.106GB/s 不变（物理下限）。
