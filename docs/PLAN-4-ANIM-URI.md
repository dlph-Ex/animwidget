# #4 动图 WebP 单 URI 推送（分两步）

> 目标：桌面组件只拿**一个** URI，launcher 的 `AnimatedImageDrawable` 自己播 →
> **零 IPC、App 退出后还在动、`PlaybackService` 可以下掉**。
> 用户已实测确认：vivo launcher 的 ImageView **会**自播动图 WebP。

## 第 1 步（v1.10.469 · 已完成）：把逐帧产物装成一个动图文件

| 项 | 落点 |
|---|---|
| 纯逻辑 | `AnimPack.java`（无 android 依赖）：`packFrames(frames, fps, out)`、`frameDurationMs`、上限与失败清理 |
| 打包时机 | `WidgetPrewarm.bakeBody` 在「全部帧烘完 + 仍是当前代」之后调 `packAnim(...)` |
| 产物 | `files/push/w<id>/<stamp>/anim.webp`（与帧文件同目录，`FrameProvider` 现成就能发） |
| 每帧时长 | `round(1000 / fps)`，下限 10ms；fps=0 按 30 兜底 |
| 闸门 | 帧数 ≤ 600、体积 ≤ 24MB；超了就删文件、日志写明原因，播放仍走逐帧推送 |
| 日志 | `W44`：`动图打包 组件=… 帧=… 每帧=…ms 大小=…KB 画布=…x… 用时=…ms` |
| 门禁 | [25] `scripts/anim-pack-check.py`（8 条 Python + 14 条 Java：Pillow 造真帧 → Java 打包 → Pillow 逐帧对像素/时长/循环） |

**这一版不改播放链**：动图文件只是落盘，播放仍是逐帧推送。先看 `W44` 的帧数/体积/耗时，
确认「文件大小和首帧时间」在可接受范围，再切推送。

## 第 2 步（下一版）：把多帧推送换成单 URI

1. `WidgetUriPush` 增加 `animUri(...)`：`FrameProvider.uriFor(widgetId, stamp, "anim.webp")`，
   推送时只 `setImageViewUri` 一次，并且**不再给这个组件排队逐帧**；
2. `PlaybackService`：对本代已有 `anim.webp` 的组件**跳过 tick**（保留类与其它职责，先不删）；
3. 回退：`anim.webp` 不存在 / 被打包闸门拒了 → 自动走原来的逐帧推送（`W44` 那条日志就是判据）；
4. 真机验收：退出 App、杀进程、锁屏解锁、换壁纸、重启桌面，看组件是否还在动；
   对比 `W10` 里的推送次数（应该从每秒 30 次掉到 0）。

## 已知风险（第 2 步之前要看的三个数）

- **文件体积**：300 帧 600×626 q95 约 12~25MB → `W44 大小=`；
- **首帧延迟**：launcher 要先读文件才能出第一帧，体感是「切回桌面先空半秒」；
- **内存**：`AnimatedImageDrawable` 按需解码，但要确认 vivo 的 ImageView 不会把整段动画读进内存
  （如果会，表现为组件被系统杀掉/白块）。

## 第 2 步（v1.10.470 · 已实施）：单 URI 推送 + 停 tick + 看门狗

| 项 | 落点 |
|---|---|
| 自播判定 | `AnimPush.ready()`：最新一代有 `anim.webp` 且 ≤ `MAX_BYTES`（16MB） |
| 推送 | `WidgetUriPush.pushAnimUri()`：`setImageViewUri(anim.webp)` 一次，grant 沿用 `grantOnce` |
| 停 tick | `PlaybackService` 在渲染分支之前拦：`AnimPush.alive()` → `pushIfChanged` + `nextAt=Long.MAX_VALUE` |
| 记忆 | 路径 + 大小 + mtime —— 换代必换这三个量，既不会重复推也不会漏推 |
| 看门狗 | 推送后 4s 内桌面**一次都没来取**（`FrameProvider.animFetched`）→ 判定这条路不通，回退逐帧 |
| 日志 | `W45 动图推送 …` / `W45 桌面取走动图 …` / `W45 动图没人取，回退逐帧 …` |
| 门禁 | [25] 扩到 16 条（新增 6 条结构断言：自播分支必须存在且必须停 tick、必须有体积上限、必须按 mtime 记忆、必须有看门狗） |

### v1.10.469 实测（用户的日志）

| 组件 | 画布 | 帧 | 每帧 | 文件 | 打包耗时 |
|---|---|---|---|---|---|
| 418 | 372×372 | 140 | 33ms | 3.5MB | 15ms |
| 418 | 286×286 | 140 | 33ms | 2.4MB | 19ms |
| 419 | 1280×720 | 235 | 20ms | 15.2MB | 39ms |

打包本身可以忽略（15~39ms），**体积**才是唯一的变量：720p/235 帧 15.2MB 仍在 16MB 上限内，
所以这一版两档都会走自播；如果真机上 720p 那档不流畅，把 `AnimPush.MAX_BYTES` 调小即可（只改一个数）。

### 真机验收

1. 导出后日志顺序应为：`W13 预热完成` → `W44 动图打包` → `W45 动图推送` → `W45 桌面取走动图`；
2. 该组件的 `W10` 应**停止出现**（不再逐帧推）；`W23` 的「渲染=」也应归零；
3. **退出 App / 杀掉进程 / 锁屏再解锁**，组件应继续动（这一条就是 #4 的全部意义）；
4. 如果出现 `W45 动图没人取，回退逐帧`，说明这台机器的 ImageView 不吃动图 WebP，
   播放会自动回到老路径（不会冻屏）。

## 470 失败记录（v1.10.471 修正）

**现象**：导出后组件**完全不播**；配置页预览也偏卡。

**日志证据**（`Component_2601_10_39.txt`）：

```
01:09:29 W45 动图推送 组件=420 帧=235 大小=16116KB
01:09:29 W45 桌面取走动图 组件=420 大小=16116KB     ← 桌面确实来取了
01:09:32 W23 … 共享=解码均28ms×6 推2 换图1         ← 之后又推了 2 张位图
01:09:33 起 W23 渲染=0 组件数=0                     ← tick 已停（按设计）
```

`推2 换图1` 来自 `W32 重推单个组件 原因=尺寸未知延后`（导出后 700ms 的那次延迟重推）
以及 onUpdate / 尺寸变化这些**一次性推送路径**。它们把刚推上去的动图 URI **覆盖成一张静止帧**，
而 tick 已经停了 —— 于是永远停在那一帧。

根的教训：**闸门只装在 tick 上不算数**。推帧的出口一共有四个（tick / 重推 / onUpdate / 拖尺寸），
只拦一个等于没拦。

### 修正（v1.10.471）

1. 闸门挪到 **`WidgetRender.render()` 第一行**（所有推送的唯一出口）：
   已自播 → 补推动图 URI 一次 → **直接 return**，任何单帧都不许再覆盖它；
   并打 `W45 已自播，跳过推帧 组件=…`（这条出现就说明闸门在起作用）。
2. 体积上限 16MB → **6MB**，并新增**帧数上限 200**：
   1280×720 / 235 帧 / 15.7MB 这一档**退回逐帧推送**（日志写
   `动图自播未启用：帧数 235 > 200`），小组件（372×372 / 140 帧 / 3.5MB）继续自播。
   在确认「桌面到底能不能播大文件」之前，宁可少一个特性，不许把组件冻住。
3. 门禁 [25] 扩到 20 条：`render()` 必须有自播闸门、体积 ≤8MB、帧数上限存在且 ≤240。

**待验证**：小组件自播是否稳定（杀进程后还在动）；720p 那档是否真的是"桌面不支持大文件"，
要等小组件这一档通过后再单独谈。

## 471 的第二处错：判定放在每帧出口，却每帧做重活（v1.10.472）

471 的日志（`Component_2601_19_03.txt`）里，同一条话出现了 **264 次、最高 50 行/秒**：

```
01:18:38~39 W45 动图自播未启用：帧数 235 > 200（大组件继续走逐帧推送）  ×264
```

原因：`AnimPush.ready()` 被 `WidgetRender.render()` **每一帧**调用（50fps = 50 次/秒），
而它每次都做了三件重活：读 SharedPreferences、`listFiles()` 扫推送目录、打一条日志。
`Diag.warnThrottled` 的 3 秒节流在这里也失效了 —— 中间夹着别的编号会把 `lastCode` 顶掉，
于是每帧都能穿过去。**这是我自己在「性能敏感路径」上放了一个 IO + 字符串拼接。**

修正（v1.10.472）：
- 判定结果按 `CACHE_MS = 2s` 缓存（`AnimPush.verdict`），`render()` 每次只做一次 HashMap 查找；
- 日志只在**结论变化**时记一条（`LAST_REASON`），换代会由 `packAnim` 调 `AnimPush.forget()` 立刻失效；
- 门禁 [25] 加一条：`AnimPush` 必须有 `CACHE_MS`（防止下次又把重活放回每帧路径）。

**这一轮同时确认的事实**（同一份日志）：
- 大组件（1280×720 / 235 帧）**已经按上限退回逐帧推送**，并且播得正常：
  `W10 组件 422 实测 50.2fps / 151 帧 / 3006ms，掉帧=0，帧隔 p50=20ms`；
- 但**没有任何小组件走过自播**（日志里没有一条 `W45 动图推送`）—— 自播这条路仍然**未验证**。

## 472 的教训：6MB 上限把正常内容全挡在外面（v1.10.473）

472 的日志（`Component_2601_33_32.txt`）只剩一条 W45（刷屏修好了），但它是：

```
01:33:11 W45 动图自播未启用 组件=423：文件 20MB > 6MB
01:33:11 W44 动图打包 组件=423 帧=172 每帧=33ms 大小=21363KB 画布=546x602
```

**546×602 / 172 帧 = 21.4MB**。我们的单帧是 q97 全画布 WebP（≈0.37 字节/像素），
所以"画布小"不等于"文件小"：6MB 这条线把所有真实内容都挡掉了，特性等于没开。

另外看清了磁盘账：`缓存=本组42807KB` ≈ 帧 21.3MB + 动图 21.4MB ——
**动图让每一代的缓存翻倍**（换代时随旧目录一起删，不会累积，但同时占用是 2×）。

修正（v1.10.473）：
- `MAX_BYTES` 6MB → **24MB**，`MAX_FRAMES` 200 → **240**（覆盖实测三档：3.5 / 15.7 / 21.4MB）；
- `W44` 增加 `均=…KB/帧` —— 判"为什么这么大"就看这一个数；
- **恢复闸**（重要）：交出过自播的组件，如果判定又失效（关掉 URI 推送 / 文件被删 /
  看门狗判死），必须把 `nextAt` 拉回"现在"，否则它永远不会再推帧（只能重启进程）。
  这条同时是**用户的逃生口**：组件冻住时把「URI 推送」关掉，约 2 秒后自动回到逐帧推送。
- 门禁 [25] 加到 22 条。

## 外部复核结论（Claude / DeepSeek，两份独立回复一致）

**1. 容器没问题，除了一处位序写反。**
libwebp `src/mux/muxread.c`：`dispose = bits&1`、`blend = bits&2`。
我们写 `0x01`（本意"不混合、不处置"）实际是"**alpha 混合 + 每帧清回背景**"；
应为 **`0x02`**。因为帧是满画布、ANIM 背景全透明，像素结果碰巧一样，所以 Pillow 那 52 条断言没抓到
——这就是"单路第三方验证"的盲点。**v1.10.476 已改成 0x02**，并把门禁 [21] 的两条断言按 libwebp 更正。

**2. 不播的真正原因（两份回复一致，且与实验 C 完全吻合）：没有人调用 `start()`。**
```
RemoteViews.setImageViewUri → ImageView.setImageURI → getDrawableFromUri
  → ImageDecoder.decodeDrawable(...)      // API 28+：isAnimated → AnimatedImageDrawable
ImageDecoder 文档原文：“A user needs to call start() to start the animation.”
而 ImageView / RemoteViews / AppWidgetHostView 里都搜不到 Animatable.start()
```
所以：**首帧能画出来（说明解码成功），但一秒都不动**。与文件大小、帧数、6MB/24MB 上限全部无关。
用户说的「会播呀」来自另一种做法：APK 内置资源走 `<animated-image android:autoStart="true">`
（那条 XML 会显式 start），对运行时素材不适用。

**3. 业界没有"运行时素材 + 单 URI 自播"的先例。**
可落地只有三条：逐帧推送（通用，我们现在这条）、`ViewFlipper`（≤20 帧短循环）、
`<animated-image>`（只能编译期资源）。

**4. 四项绝对性在物理上不可能同时满足。**
按实测吞吐反推：`50.2fps × 1280×720 = 46.1 Mpx/s` 是这台设备的天花板；
`50fps × 1920×1080 = 103.7 Mpx/s` 是 2.25 倍，物理不可达。
另外"1:1 原文件"本身不成立：组件只有 879×869 px，1080p 素材在 fitCenter 下只显示 879×494。
**可验证的口径应改为**：`画布像素 ≥ 组件像素` 且 `画布像素 × fps ≤ 46 Mpx/s`（高帧率与高清二选一）。

**5. 我方文档的数字订正**：每帧字节数不是 0.37 B/px，实测 `16116KB / 235 帧 / 921600px = 0.074 B/px`；
样本时长是 33/34/33（不是 33/33/34）。
