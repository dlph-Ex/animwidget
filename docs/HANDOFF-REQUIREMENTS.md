# 需求书：桌面组件「拖动尺寸 → 1s 适配 + 不裁 + 不中断 + 原清晰度」怎么才能同时成立

> 交给外部 AI 的问题清单。项目：帧工坊 FrameSmith（`io.github.animwidget`），源码 `src-v2/`。
> 构建：`bash scripts/build-apk-src.sh <versionCode> <versionName>`；门禁：`bash scripts/verify-apk.sh dist/xxx.apk`（12 项，必须全绿）。
> **没有 Gradle / Android SDK / adb**，只有 aarch64 PRoot + JDK17 + `toolchain/`（aapt2、r8、apksig）。真机只有一台，用户自己装。

---

## 1. 用户硬性要求（原话，不可打折）

### 三类素材共同项
- 1080p ≤、50fps ≤、40s ≤ → 默认参数 → **1:1 = 预览 = 原清晰度 / 原 fps / 原时长 / 原播放速度**；**桌面组件 = 同预览**
- 导出 →（非应用端保存）→ **组件先显示画面第一帧 → 正常播放**
- ≥1080p → 清晰度参数 = 精转清晰度
- ≥50fps → 默认/30~50fps = 精转 fps；**播放速度与时长误差到小数点后 2 位**
- ≥40s → 禁止导入
- 图片：2.5K ≤ → 1:1 = 预览 = 原清晰度；≥2.5K → 精转
- **拖动组件大小 → 画面 1s 内自动适配组件大小**
- **非「填充」模式下：用户视角不得有任何"例外的"缩放/截断/裁剪，必须显示完整画面**
- 播放不中断；清晰度恢复要快

### 已被证实成立的部分（不要重做）
- 几何：画布比例 = 真实格子比例（`AT_MOST` + `intrinsic` 机制已搞清，见 `HANDOFF-WIDGET-FIT.md`）
- 不裁：`FrameComposer.contentRect()` 对 FIT 走 `autoContentRect()`（内接，一个像素不裁）
- 导出→首帧、时长误差 0.18%（`T26` 日志）、预览=源分辨率（`V10/P02` 日志）

### 唯一没解决的矛盾（本需求书要解决的）
**50fps × 813×1079 格子（87.7 万像素）× 1:1 清晰度 × 播放不中断** —— 四者不能同时成立，
瓶颈是**逐帧编码吞吐**，不是渲染，也不是桌面。

## 2. 现场实测数据（vivo V2426A / Android 16 / 1260×2800 / density 3.28 / 桌面包 `com.bbk.launcher2`）

### 2.1 桌面侧机制（已定案，别再试）
- 桌面用 `AT_MOST` 量 RemoteViews；`ImageView.onMeasure` 取 `min(drawable.intrinsic, specSize)`
- `intrinsic = 位图像素 × density/160`（实测 ×3.28）
- 结论：**画布像素 = 格子像素 → 屏幕 1:1；画布 < 格子 → 被放大（糊）**
- `RemoteViews.setViewLayoutWidth/Height` 被 vivo 忽略（实测）
- vivo 报的 `min/maxWidth/Height(dp)` **不含它自己的内边距**：报 314×329dp，实测白框 334×334dp（宽 +20dp、高 +5dp）

### 2.2 预热吞吐实测（q97 WebP，6 线程，`W13 预热完成` 原文）
| 画布像素 | 面积 | 聚合速率 | 单帧线程耗时 |
|---|---|---|---|
| 380×853 | 32 万 | **47 fps** | ~127ms |
| 597×853 | 51 万 | **26 fps** | ~230ms |
| 813×853 | 69 万 | **21 fps** | ~285ms |
| 900×745 | 67 万 | 34 fps（300 帧/8.8s） | ~175ms |
- 编码单独计时（`W27`）：**q97 单帧 154ms @ 约 90 万像素**（`编码均=154ms`是**每帧平均**）
- 播放需求：50fps = 每帧 20ms
- **⇒ 能持续供帧的画布上限 ≈ 28~30 万像素**（47fps ≈ 50fps）

### 2.3 播放侧
- `W10 组件 237 实测 49.3fps 命中=0%(1/148) 跳过=65 顶帧=82` —— 帧率数字好看，但内容大半是重复/旧帧
- 环形烘（从播放头 +10 帧开始）已实现，`首帧命中 距画布变化=1684ms`（其中静置 1502ms，已改 400ms）

## 3. 已排除的方案（都试过或有实测依据，别重复）

| 方案 | 为什么不成立 |
|---|---|
| 调 `scaleType` / 画布比例 | 位图小于格子时，尺寸由 intrinsic 决定，与 scaleType 无关 |
| `setViewLayoutWidth/Height` 钉死视图 | vivo 忽略该调用（实测卡面仍 70%） |
| 衬底（把同一帧缩到 1/8 再放大铺满四周） | 透明底素材会从透明区透出，形成沿轮廓的灰雾 |
| 「按需滚动窗口 + 删播过的帧」 | 播放是 `due=(elapsed×fps)%count` 正向循环，删了每圈都要整盘重烘 ≈ 5 核满载 |
| 提高线程数 6 → 8 | 只 +33% 聚合吞吐；26fps → 35fps，仍 < 50，且抢 UI |
| 压编码质量 q97 → q90 | 编码 −35% 左右，87.7 万画布仍只有 ~40fps（差 50），且叠加二代有损 |
| 压画布到 24~28 万 | **能成立但不满清晰度**：813×1079 格子上是 1.7× 放大 |
| 降低播放帧率到 26fps 换 1:1 | 画面清晰但用户明确要求"原 fps / 原时长 / 播放速度" |
| 用缩略图/静态背景 + 局部动画 | 全画幅视频没有"局部"，会破坏内容 |

## 4. 待探索方向（外部 AI 请从这些里找，或提出新路）

1. **编码格式/参数**：WebP q97 是否最优？实测 q97 单帧 154ms @90 万像素，能否用
   `RGB_565` 输入、`WEBP_LOSSY` 低质量 + 后处理锐化、或 **PNG 调色板/量化**（8-bit）把编码压到 60ms 级？
   目标：**87.7 万像素编码 ≤ 90ms**（6 线程 → 66fps，能追 50fps）。
2. **避开逐帧编码**：能否把帧以**未压缩/低开销格式**落到 `ContentProvider`，让桌面自己解码？
   （桌面只认图片 URI；`openTypedAssetFile` 返回 Bitmap 是否可行？binder 1MB 限制？）
3. **多画布桶（aspect buckets）**：格子比例吸附到 1/16 档，重复尺寸直接复用已烘好的整盘，
   减少"每次拖动都重烘"。代价：比例差 ≤0.5% 的裁切（用户对 2.3% 已经很敏感，需实测 0.5% 是否可接受）。
4. **解码侧**：`MediaMetadataRetriever` 逐帧解码 1080p 每帧 ~15~20ms，是否能用
   `ImageDecoder`/`MediaCodec` 直接出 **缩放到目标尺寸** 的位图（省一次 `createScaledBitmap`）？
5. **合成侧**：`FrameComposer` 每帧 4ms（含 clipPath），若把形状蒙版改成**一次性 alpha mask 位图**（`setXfermode`），
   能否把合成压到 1ms 以内，把省下的都让给编码？
6. **播放侧自适应**：若吞吐确实追不上，能否**只对"落后太多"的帧降采样**（每 2 帧推 1 帧，但时间轴仍按 50fps 走）？
   用户要求"播放速度不变"，这条例仍需验证。
7. **两段式编码**：T0 秒出（8 万像素）+ T1 稳定（28 万像素）+ **T2 仅烘"关键帧"**（每 10 帧一张 87.7 万），
   播放时用 T1 插值、关键帧替换 —— 观感是否可接受？

## 11. 待修：「超长组件」（极扁/极宽格子）仍然截断

实测（21:10，组件 249，素材 800×720 = 1.111）：

```
画布=800x303(2.640)  格子=1095x416(2.632)  画面=323x291（占格子宽40%、高96%）
画布=800x469(1.706)  格子=1095x643(1.703)  画面=500x450（占格子宽63%、高96%）
画布=662x643(1.030)  格子=662x643(1.030)   画面=636x572（占格子宽96%、高89%）
```

两个独立缺陷：

1. **画布被素材尺寸锁死**：`canvasForSource()` 用"素材最长边"封顶，素材 800 宽 → 格子 1095 宽时画布只有 800
   → 桌面放大 1.37×（糊），宽高比也只能近似（2.640 vs 2.632，0.3%）。
   极扁格子下这点比例差被放大成**可见的边裁**。
2. **格子尺寸本身就是估计值**：vivo 不提供 `OPTION_APPWIDGET_SIZES`，我们用
   `min/maxWidth/Height(dp) + 固定 padding(+20dp/+5dp)` 反推。**固定 dp 补偿在极扁/极宽格子上相对误差最大**
   （宽 314+20、高 122+5，两个方向的相对修正量不同）→ 真实比例与估计比例偏离 → 桌面 centerCrop 裁到画面。
   v1.10.297 加了"画面四周留 2% 安全边"缓冲（≤4% 的裁切伤不到画面），但**极扁时误差可能超过 4%**。

### 要求外部 AI 解决的点
- 想一个**不依赖 vivo 提供真实格子尺寸**的办法，让画面在任何长宽比下都 100% 不被裁；
  可用方向：从 `RemoteViews` 回读尺寸（不可用）、用 `AppWidgetHostView` 的可见区域（不可用）、
  **让桌面永远不需要裁**（画布比例由我们自己按"最保守"的格子反推：取 min/max 的四种组合里最宽和最窄各做一版）、
  或**放弃 centerCrop**：把画布做成"任意比例都能内接"的容器（四周透明），让桌面 fitCenter ——
  代价是要能控制 scaleType（`RemoteViews` 只能按布局 XML 定 `widget_media` / `widget_media_fit`，可用）。
- 顺带修：极扁格子上画布被 `canvasForSource` 封顶导致糊（应允许按格子宽度放大画布，代价是编码变慢，
  但 140 帧的素材可以接受）。

### 验收
极扁（宽高比 ≥ 2.6）、极宽（≤ 0.4）、近方（≈1.0）三种格子各拖一次：画面**不得有任何一个像素被切**，
且画面占比与"素材比例 / 格子比例"的算术值误差 ≤1%。
