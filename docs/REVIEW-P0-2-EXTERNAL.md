## 0. 一句话

**P0-2「不透明内容帧 JPEG + 常驻 alpha overlay」否决。**
它在我们的默认档（圆角蒙版 + 阴影 100）里**几何上不成立**；而它成立的档位，我们 **v1.10.292 起早就在走 JPEG**。两份复核独立得出同一结论，我用我们自己的几何复算并出图证实（`/chat/outputs/p0-2-overlay-probe*.png`）。

## 1. 两条纠正：比结论本身更重要

### 1.1 「每帧解码 12~13ms 在 launcher 侧」是错的 —— 那 13ms 在我们自己进程里

代码路径（v1.10.410 起）：

```
PlaybackService.tick → WidgetUriPush.submitDecode → DecodeTask.run
  → decodeFrameFile(uri)              // FrameProvider.fileOf → 本地 File
      → decodeShared(f)               // ImageDecoder + ALLOCATOR_SHARED_MEMORY
      → b.asShared()
  → RING.complete(...)；BMP_MS/BMP_LAT 记的就是这一段
```

日志 `共享=解码均13ms×… 直解=173/172 零拷贝=173` 的含义：
- `直解=173/172` = 173 次解码全走了直解共享；
- `零拷贝=173` = `asShared()` 返回**自身**（像素本来就在 ashmem）⇒ 没有额外拷贝；
- `解码均` 与 `延迟均` 的差 = 排队。

**结论**：`传输=位图共享` 这条通道上，解码成本 100% 由我们支付。
两个后果：
1. 「共享位图是为了把解码搬离桌面」这个立项理由，在**单路 720p** 档上早已兑现（桌面不解码了），成本已经搬到我们自己头上——W10 好看不代表我们便宜。
2. `W47` 的 **46.1 Mpx/s** 是**我们自己的解码吞吐上限**，不是桌面的 64M。W47 里那句「%上限」要按前者读。

### 1.2 「§2 耦合（阴影要量内容的不透明包围盒）」是过期文档

`FrameComposer.java:124` 还留着 v1.8.6 的注释，但**代码里没有这件事**：

- `acc[]` 只累计耗时（`acc[0]` 阴影、`acc[1]` 内容+裁剪）；
- 阴影走 `ShadowLayer.obtain(localPath, boxW, boxH, …)`，只吃**形状路径 + 强度**，跟内容像素一点关系都没有。

所以 Claude 那句「阴影/边框本来就能分层，不需要『内容必须不透明』这个前提」**成立**；DeepSeek 的「两件事实为条件」对应的是我们的旧代码，不是现在。

**但这不救 P0-2**：分层的障碍从来不在阴影，在**内容自己的 alpha**。

## 2. 为什么不成立（一屏代数 + 我们自己的数）

分层后最终颜色 `T = O + C·(1 − O_α)`（over 结合律）。
JPEG 内容帧 ⇒ 在内容矩形内 `C_α ≡ 1`，于是**矩形内、形状外**的那一圈（圆角三角 + 阴影带）必然 `T = C`，与壁纸无关。
要让 `T` 与 `C` 无关，只能 `O_α ≡ 1`（overlay 不透明）—— 那阴影就变成不透明块，壁纸被挡住。这是另一个产品。

我们的真实几何（`879×869` 画布、`1280×720` 素材、原始比例、阴影 100、圆角）：

| 档 | 内容框 | 圆角半径 | 四角方角面积 |
|---|---|---|---|
| 原始比例（有 letterbox） | 723×406 | **73.2 px** | 4597 px²（0.60% 画布） |
| 铺满 | 879×869 | **140.6 px** | 16969 px²（2.22% 画布） |

像素实测（**叠壁纸比**，3 张壁纸 = 浅/深/照片，RGB 通道最大差）：

| 方案 | 档 | >8 的像素 | 最大差 |
|---|---|---|---|
| B：不透明内容 + overlay | 原始比例 | 0.73 ~ 0.84% | 92 ~ 211 |
| B：不透明内容 + overlay | 铺满 | 1.73 ~ 2.53% | 37 ~ 213 |
| C：分层但**内容自己带 alpha** | 两档 | 0.21 ~ 0.29% | 32 ~ 63 |

> 画面内容是**程序合成**的一帧（16:9、四角都有色彩与纹理），不读任何用户素材 ——
> 早先那版拿过工作目录里的一张截图当内容，被用户当场指出，已改掉。
> 「photo」那张壁纸因为与内容同源、颜色接近，差值会偏小（甚至 &lt;40 的占比接近 0），
> 所以判据要三张壁纸一起看；而**与颜色无关**的那部分才是几何事实：
> **四角方角面积 = 0.60%（原始比例）/ 2.22%（铺满）的画布像素，其来源从「壁纸」变成了「内容」**。

- **B 的失败是定性的**：73px 半径的直角 + 阴影压在画面上。面积只有 0.6% 却一眼就能看出来（见 `p0-2-overlay-probe-corner.png` 中间那块），差异热图里就是四个红角。
- DeepSeek 报的 63% 是他们「内容铺满整块画布」的口径；我们的内容矩形 = 蒙版 bounds（723×406），**不会铺满**，所以面积小得多，但破坏性一样。
- **C 的 0.25% 是脚本自己的 1px 抗锯齿环**（旧帧里阴影在内容下面、分层后阴影在内容上面，AA 边缘必然差一档）。这条正是「我方进程内合成」那条路的外观代价 —— 肉眼不可见。

## 3. 为什么增益本来也 ≈ 0

v1.10.292 起：**整帧 alpha 全 255 ⇒ 走 JPEG**（`alphaState` 粘性判定 + `HIRES_AREA` 1:1 档）。

P0-2 的**有效域**（shadow=0 + 形状铺满 + alpha=100 + 无 letterbox + 素材无 alpha）**正好就是** `alphaState` 已经在走 JPEG 的那个域。
两个集合重叠 ⇒「圆角配置靠 P0-2 提速」这个前提本身不成立。外部这条判断是对的，我们有代码为证。

## 4. 还站得住的形态：把分层放进**我方进程**，不放进布局

不是「桌面叠两张图」（那样必露方角），而是：

```
解码：JPEG（内容矩形，快）
合成：用常驻蒙版（烘一次：阴影 + 圆角 + 挖洞）把它裁回成品形状 —— 一次 blit + 一次 DST_IN
推送：asShared() → setImageViewBitmap（桌面零解码，和现在一样）
```

外观等价于上表 **C 行**（0.25%，仅 1px AA 环，肉眼不可见）。
这条路成立与否，全押在一个数上：**JPEG 解码比我方现在的 WebP 解码快多少**。
外部给的 4.7ms vs 23.5ms 是别人的机器；Claude 明确说没有证据、要先做实验。所以 → 第 6 节。

## 5. 判据修正（外部指出的两个洞，都对）

1. **`W46`「层内合成自检」恒等于 0**：三张图层按顺序叠回同一张透明画布，必然等于旧帧。真实差异发生在**桌面把两张纹理合成**的时候。判据必须改成**叠壁纸比**：
   `over(over(wall, content), overlay)` vs `over(wall, 旧帧)`，至少 3 张壁纸。
   → 已实现：`scripts/p0-2-overlay-probe.py`（本文第 2 节的数字与图都是它算的）。**不再做 W46 那个假自检。**
2. **`W47` 四项都不测外观**：方案改成「方角满铺」也会全绿。建议加第 5 项「外观指纹」。
   → 暂未实现：如果最终走第 4 节的「我方进程内合成」，门禁用**同一套像素对拍**（合成结果 vs 烘好的帧，逐像素）比指纹硬得多；指纹只在「布局里真的多了一层」时才有意义，而那条路已经否决。

## 6. 这一版（v1.10.478 / vc592）做了什么

**只加测量，不改任何播放/渲染行为。**

| 新增 | 作用 |
|---|---|
| `DecodeBench.java` + `BenchMath.java` | 每代烘焙末尾跑一次（约 50ms），打 `W48` |
| `DiagCatalog` W48 条目 | 日志口径 |
| `scripts/decode-bench-check.py`（门禁 [26]，28 条 + Java 29 条） | 钉住「测法本身不许骗自己」 |
| `scripts/p0-2-overlay-probe.py` | 叠壁纸比 + 出图（本文第 2 节） |
| `tests/BenchMathTest.java` | 中位数 / 单位 / 判据方向 |

`W48` 测法（同一张成品帧、同一线程、同一像素数、5 次取中位数）：

```
解码对拍 组件=425 帧=117/235 画布=879x869 WebP=13.0ms JPEG=5.0ms 合成=2.0ms 合计=7.0ms 省=46% 判据=JPEG+合成更便宜
```

（v1.10.479 修正：毫秒改一位小数、门槛从 10 万 px 降到 4 万 px、超门槛时**必打一行「跳过」**。
478 那两个门槛把真机上那一代（240×240=57.6k、286×286=81.8k）整个吞掉，日志里连一行都没有。）

判读：
- `合计 = JPEG + 合成` **明显小于** `WebP` → 第 4 节那条路值得做；
- 不小于 → 瓶颈不在解码器（在 IO / 排队），换编码没用，那时该看 `W10` 里 `延迟均 − 解码均`；
- `WebP` 与 `JPEG` 只差 alpha 却几乎一样（如 13 vs 12）→ 印证外部那句「JPEG 快在编码器，不在没有 alpha」，那么「去掉 alpha 更快」这一类推断以后都不许再用。

## 7. 下一步（等用户拍板，不自行开工）

| 选项 | 内容 | 收益 | 风险 |
|---|---|---|---|
| **A** | **共享解码 N→1**（同素材多路只解一次，`BMP_MAP` 的 key 改成全局 asset+stamp+canvas） | 同素材 4 路：解码核 2.6 → 0.7，观感零变化 | 中：跨组件生命周期/回收要重写；多路**不同素材**无收益 |
| **B** | 我方进程内 JPEG + 常驻蒙版合成（第 4 节） | 单路解码 13 → 5~7ms（**等 W48 证实**） | 中：热路径改动、每帧多两次全画布 blit，要实测 GPU/CPU blit 成本 |
| **C** | 不做这两条，转 **#10 预览管线**（JPEG + 静态蒙版检测，只影响配置页） | 配置页更顺 | 低，但对桌面播放无收益 |
| **D** | 只修判据（W47 加外观项等） | 无收益，只是以后不再被判据骗 | 低 |

我的建议：**先看 W48 那一行**。
- 若 `省 ≥ 30%` → 走 B（它同时解决「圆角」与「解码贵」两个问题，且不动布局）；
- 若 `省 < 30%` → 走 A（那说明瓶颈是「每帧都要解一张」而不是「解码器慢」，N→1 才是唯一能同时降 N 和 CPU 的改动）。
